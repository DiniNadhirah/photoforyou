# What changed from v1 to v2

Use this for the **Difficulties** and **Enhancements** slides.

## Problems found in v1

| # | Problem in v1 (`app.py`) | Risk | Fix in v2 |
|---|---|---|---|
| 1 | All users' files were saved in **one flat bucket folder under the original file name** (`IMG_0001.JPG`) | Two users uploading the same name collide (upload fails or overwrites). The storage looks messy and isn't separated by account. | Files are stored at `<user_id>/<random-uuid>.bin`: one folder per account, and names can never collide |
| 2 | **Public bucket**: images shown with `/storage/v1/object/public/Photos/<filename>` | Anyone with, or guessing, a file name could see the photo without logging in | **Private** bucket. The browser only gets **signed URLs that expire in 1 hour**, after a login and ownership check |
| 3 | `/download/<filename>` did **not** check the owner | Any logged-in user could download another user's photo by typing its name | Every route looks the file up with `user_id = logged-in user` first, otherwise 404 |
| 4 | `/delete/<id>/<filename>` removed the storage file **before** checking the owner | Any logged-in user could **delete** another user's photo | Ownership check first, then delete the database row and the storage files |
| 5 | File names were put inside JavaScript `onclick='…'` | A crafted file name could run JavaScript (**XSS**) | No user data inside scripts. Names are rendered with `textContent`, and a strict **Content-Security-Policy** blocks inline scripts |
| 6 | `app.secret_key = 'super-secret-key-photoforyou'` in the code | Anyone reading GitHub could forge a login session | `SECRET_KEY` comes from an environment variable, generated by Render |
| 7 | Delete was a plain link with `confirm()`, and forms had no CSRF token | Another website could trigger deletes or uploads (**CSRF**) | CSRF tokens on every form and API call. Delete uses the `DELETE` method with an in-page confirmation |
| 8 | Rename downloaded and re-uploaded the whole file, always as `image/jpeg` | Slow, and corrupted PNG/HEIC/videos | Rename only changes the (encrypted) name in the database |
| 9 | No size or type checks, one file per upload, images only | Huge or wrong files, poor experience | Type allow-list (photos + videos), 50 MB per file, **200 MB quota per user**, multi-file upload with progress |
| 10 | Folder names typed freely ("Study" vs "study ") | Duplicate folders | Spaces trimmed, case-insensitive match to an existing folder, dropdown suggestions |
| 11 | No order, no search | Gallery hard to use | Folders A–Z, sort by newest/oldest/name/size, search |
| 12 | Management (Supabase project owners) could open every photo | No privacy from the team | **End-to-end encryption**: photos, thumbnails and file names are encrypted in the browser with a key only the user has |
| 13 | One instance, no limits | No traffic handling (the lecturer's comment) | nginx load balancer, failover, health checks, rate limiting, caching; tested with Locust |

## Problems we hit while building v2 (and the fix)

| Difficulty | Cause | Fix |
|---|---|---|
| A login on instance A was not recognised by instance B | Each instance had its own random secret key | All instances share one `SECRET_KEY` (Render env group) |
| Render free plan allows only one instance per service | Free plan limit | Two separate services (A, B) plus our own nginx load balancer service |
| nginx can't reach Render services over a private network | Free services have no private networking | nginx connects to each instance's public HTTPS address through a small local "bridge" per instance |
| Every user looked like the same IP to the app, so one user's rate limit blocked everyone | Requests arrive from the load balancer's IP | nginx passes `X-Client-IP`. The app trusts it **only** with the matching secret `LB_TOKEN` |
| Forms failed with a CSRF error behind the load balancer on HTTPS | Flask-WTF's strict Referer check compared the LB host with the instance host | Turned off the Referer check (`WTF_CSRF_SSL_STRICT=False`); the CSRF token check still applies |
| HEIC photos show no thumbnail in Chrome | Chrome cannot decode HEIC | The original is still saved, with a labelled placeholder. Safari/iPhone shows them |
| Server can't make thumbnails of encrypted photos | The server never sees the real photo | Thumbnails are made in the browser before encryption, then encrypted too |
| Uploads that were in progress on a crashing instance failed | nginx does not resend uploads (POST), to avoid saving twice | Correct behaviour: the user sees an error and retries (1 in 10,982 requests during the failover test) |
| The load-test tool sent all requests from one IP and got rate limited | All simulated users ran on one machine | Each simulated user sends its own `X-Forwarded-For` address, trusted only from localhost |
